# V5 Dataset Construction

## Source Data

- **Judgments**: `outputs/v3/evaluation_judgments.csv` (52,423 query-product pairs)
- **Queries**: `outputs/v3/evaluation_queries.csv` (1,000 complete query groups)
- **Catalogue**: Bounded 5,000-product live demo catalogue
- **Seeds**: 42, 52, 62, 72, 82 (group-safe)

## Split Methodology

Splits are generated by `v3_evaluate.splits()` using the existing group-safe
seed framework. Each seed defines train/validation/holdout query groups with
zero term_id overlap.

- **Train groups**: Used for any fine-tuning (if applicable)
- **Validation groups**: Used for hyperparameter and alpha selection
- **Holdout groups**: Used for final evaluation only

## Candidate Pair Construction

Pairs are constructed from Hybrid RRF candidate pools (pool sizes 20, 50, 100).

For each query:
1. Retrieve top-100 Hybrid RRF candidates
2. For each candidate, extract: query, item_id, title, category, brand,
   gender, age_group, attributes, fused_rank, retrieval_score
3. Assign relevance label from judgments (1 = relevant, 0 = not relevant)
4. Build document text using bounded templates

## Document Variants

- **A. title_only**: Query + title
- **B. title_category**: Query + title + category
- **C. title_category_brand**: Query + title + category + brand
- **D. title_compact_metadata**: Query + title + category + brand + attributes (truncated to 240 chars)

## Leakage Prevention

- No same query group appears in train, validation, and holdout
- No weight tuning on holdout
- No model selection on holdout
- No early stopping using holdout
- Alpha grid selection uses validation groups only

## Pair Counts

- Pool 20: ~20,000 pairs (1,000 queries × 20)
- Pool 50: ~50,000 pairs (1,000 queries × 50)
- Pool 100: ~100,000 pairs (1,000 queries × 100)

## Label Distribution

Labels are binary (0 = Alakasız, 1 = Alakalı). The dataset is imbalanced:
most candidates are non-relevant (label 0). This is expected for retrieval
candidate pools where only a few items per query are relevant.

## Reproducibility

All pairs are deterministic: same query + same candidate pool always produces
the same pair set. The `build_pairs()` function in
`search_pipeline/cross_encoder_contracts.py` ensures deterministic construction.

## Output Files

- `outputs/v5/v5_candidate_pairs.csv`: All candidate pairs with labels
- `outputs/v5/v5_query_metrics.csv`: Per-query metrics for all policies
- `outputs/v5/v5_metrics_by_seed.csv`: Per-seed aggregated metrics
- `outputs/v5/v5_repeated_seed_ci.csv`: Repeated-seed confidence intervals
- `outputs/v5/v5_paired_bootstrap.csv`: Paired bootstrap comparisons
- `outputs/v5/v5_paired_deltas.csv`: Paired delta summaries
- `outputs/v5/v5_results.json`: Overall results and metadata
